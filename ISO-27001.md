# ISO 27001 Compliance Strategy for Atalaia

## 1. Introduction

It is critical to understand that **ISO 27001 certifies an organization's Information Security Management System (ISMS), not an individual application.**

This document outlines how the Atalaia application is developed, operated, and maintained to align with the controls and best practices required by an ISO 27001-compliant ISMS. The goal is to ensure that Atalaia, as a critical information asset, adheres to the organization's security policies and procedures.

The following sections map specific actions and processes for Atalaia to the relevant controls in ISO 27001:2022 Annex A.

## 2. Asset and Risk Management (Annex A.5 & A.8)

**Objective:** To identify information assets and manage associated risks systematically.

*   **A.5.9 - Inventory of Information and Other Associated Assets:**
    *   **Action:** Maintain a formal inventory of all assets associated with the Atalaia service. This includes:
        *   Source code (Git repository).
        *   Production environment (e.g., Docker container, cloud instance).
        *   Configuration files (`config.json`, `config/technologies.json`).
        *   Secrets (e.g., `SLACK_WEBHOOK_URL`, `API_KEY`, `OPENAI_API_KEY`, SMTP credentials).
        *   Data assets (SQLite database at `data/atalaia.db`).
        *   Documentation (`README.md`, `ISO-27001.md`, `CHANGELOG.md`).

*   **A.8.2 - Information Security Risk Assessment:**
    *   **Action:** Conduct and document a formal risk assessment for the Atalaia application. This process identifies threats, vulnerabilities, and potential impacts on confidentiality, integrity, and availability.
    *   *Example Risk:*
        *   **Threat:** Unauthorized access to the Slack webhook URL.
        *   **Vulnerability:** Secret stored in an unsecured `.env` file on a compromised server.
        *   **Impact:** Malicious actor could post false alerts, causing disruption (loss of integrity and availability of the communication channel).

*   **A.8.3 - Information Security Risk Treatment:**
    *   **Action:** For each identified risk, a risk treatment plan is in place. Options include mitigating the risk (e.g., using a secrets vault), accepting it (with formal approval), transferring it, or avoiding it.

## 3. Secure Development (Annex A.8)

**Objective:** To ensure that information security is an integral part of the software development lifecycle.

*   **A.8.25 - Secure Development Life Cycle:**
    *   **Action:** All changes to the Atalaia application must follow a secure development process:
        1.  **Branching:** All work is done on separate feature branches.
        2.  **Change Management:** Direct pushes to the `main` branch are prohibited.
        3.  **Peer Review:** All changes must be submitted via a Pull Request (PR) and require at least one approval from another team member.
        4.  **Testing:** Automated tests (where applicable) must pass before merging.

*   **A.8.26 - Application Security Requirements:**
    *   **Action - Dependency Scanning (SCA):** The `npm audit --production` command is integrated into the CI/CD pipeline. A formal process exists to triage and remediate critical vulnerabilities in third-party packages within a defined SLA (e.g., 7 days).
    *   **Action - Secrets Management:** The `SLACK_WEBHOOK_URL` and other secrets must not be stored in plaintext files in production. The application is configured to fetch secrets at runtime from a secure vault (e.g., AWS Secrets Manager, HashiCorp Vault, Azure Key Vault).

## 4. Access Control (Annex A.5)

**Objective:** To ensure that access to information and systems is limited to authorized users.

*   **A.5.15 - Access Control:**
    *   **Action - Source Code:** Access to the source code repository is managed based on the principle of least privilege. Write access to the `main` branch is restricted to a small number of authorized personnel.
    *   **Action - Production Environment:** Access to the production server/container where Atalaia runs (e.g., via SSH, cloud console) is strictly controlled, logged, and reviewed periodically. Multi-factor authentication (MFA) is enforced for all administrative access.

## 5. Security Operations (Annex A.8)

**Objective:** To ensure the secure operation of information processing facilities.

*   **A.8.16 - Monitoring Activities:**
    *   **Action:** Application logs are not stored locally on the container. They are streamed to a centralized, secure logging platform (e.g., AWS CloudWatch, ELK Stack, Splunk).
    *   **Action:** The logging platform is configured to protect the integrity of the logs (preventing modification) and to generate alerts for critical application errors or security events.

*   **A.8.23 - Web Filtering & A.8.9 - Configuration Management:**
    *   **Action - Data in Transit:** All HTTP requests made by Atalaia (to feeds and to Slack) must use HTTPS (TLS 1.2 or higher).
    *   **Action - Data at Rest:** The SQLite database (`data/atalaia.db`) and any other data stored at rest must reside on an encrypted volume (e.g., AWS EBS with encryption enabled).

## 5.1 API Authentication and Authorization

*   **API Key Authentication:** All REST API endpoints under `/api/v1` require an `X-API-Key` header matching the `API_KEY` environment variable. Unauthenticated requests receive HTTP 401.
*   **Slack Signature Verification:** Slack interactive message payloads are verified using HMAC-SHA256 with the `SLACK_SIGNING_SECRET`, with a 5-minute timestamp window to prevent replay attacks.
*   **Security Headers:** All responses include `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Strict-Transport-Security`, and `Referrer-Policy`.
*   **CORS:** Configurable allowed origins via `CORS_ORIGINS` environment variable.

## 5.2 Data Flow and Retention

*   **Data Flow:** Vulnerability data flows from external feeds through the application layer into a local SQLite database. New vulnerabilities trigger Slack notifications and optional LLM processing.
*   **Status Lifecycle:** Vulnerabilities follow a controlled lifecycle: OPEN -> ACKNOWLEDGED -> RESOLVED. All transitions are logged with the actor (`changedBy`) and timestamp.
*   **Data Retention:** RESOLVED vulnerabilities remain in the database for audit purposes. A future cleanup job can purge records older than a configurable retention period.
*   **Audit Trail:** All status changes, API requests, and system events are captured via Pino structured logging (JSON format in production).

## 5.3 LLM Data Handling

*   **Data Sent to LLM:** When configured, the following vulnerability fields are sent to the LLM provider for explanation generation: CVE ID, title, description, severity, CVSS score, exploit status, and affected technologies.
*   **No PII:** No personally identifiable information is sent to LLM providers.
*   **Provider Control:** LLM integration is opt-in via the `LLM_PROVIDER` environment variable. When not configured, a NoOp provider is used and no data leaves the system.
*   **Local Alternative:** The Ollama provider enables fully local LLM processing, ensuring no data leaves the organization's network.

## 6. Incident Management (Annex A.6)

**Objective:** To ensure a consistent and effective approach to the management of information security incidents.

*   **A.6.3 - Information Security Incident Management Planning and Preparation:**
    *   **Action:** A documented incident response plan exists for potential security events related to Atalaia.
    *   *Example Scenario: Leaked Slack Webhook URL*
        1.  **Identification:** The incident is detected.
        2.  **Containment:** The compromised webhook is immediately revoked in the Slack admin panel.
        3.  **Eradication:** The root cause of the leak is identified and fixed.
        4.  **Recovery:** A new webhook is generated and securely deployed using the approved secrets management process.
        5.  **Lessons Learned:** A post-mortem is conducted to improve processes and prevent recurrence.
